# FP vs FX64 in an End-to-End Parameter Search — Wall-Clock Result

**Verdict: margin present. FX64 is faster by 86.72 % of FP's wall clock
(a 7.53x ratio), against a 2.85 % threshold.**

Both implementations were proved to compute bit-identical answers — the same
`hits` for all 100 002 candidates, the same `best_z`, the same `best_D` bit
pattern — before any timing was produced.

**Frequency governance is a stated limitation.** Under WSL2 the guest exposes
no `cpufreq` or `intel_pstate` sysfs, so the governor and turbo state could
neither be read nor pinned from inside the benchmark; frequency is managed
entirely by the Windows host. This is mitigated but not eliminated by the
design: all 30 invocations were interleaved in a fixed random order on the same
pinned core within a few seconds of each other, and the headline figure is a
*ratio* of two wall-clock medians, which is insensitive to a clock offset that
applies equally to both. It is not insensitive to a clock that drifts
systematically between variants, which is why the interleaving matters.

### Separation proof

Both load-bearing preconditions are **asserted by the generator**, not assumed.

**`T` is not a multiple of `N`.** `x_t = ((t*z) mod N)/N`, and `gcd(z,N)=1`
makes multiplication by `z` a permutation of the residues, so over a full
period `t = 1..N` every candidate would visit every residue exactly once and
`hits` would be the same constant for all `z`. `T % N = 1000 != 0` and
`T = 1000 << N = 100003`, so each candidate visits a `z`-dependent subset and
`hits` genuinely discriminates.

**`eps*N` is not an integer.** Reachable points are exactly `k/N`; an integral
`eps*N` would put one of them precisely on a window edge, where FP drift and
FX64 rounding could fall on opposite sides. The exact closest approach is
`min_k |k*Q - E*N| / (N*Q)`:

```text
eps*N                 = 2100063/2000 = 1050.0315      (not an integer)
min_k |k*Q - P*N|     = 63                            (lower edge, eps)
min_k |k*Q - (Q-P)*N| = 63                            (upper edge, 1-eps)
edge clearance        = 63/200006000 = 3.149906e-07

FP   drift bound      = 2*T*2^-53    = 2.220446e-13   safety ratio 1.4186e+06
FX64 drift bound      =   T*2^-65    = 2.710505e-17   safety ratio 1.1621e+10
```

The FP bound charges `2^-53` to the rounding of `alpha = fl(z/N)` and `2^-53`
to each of the `T` additions; the conditional `- 1.0` is exact because it
cancels within a single binade. No reachable point comes within six orders of
magnitude of an edge, so FP, FX64 and exact integer arithmetic are *forced* to
identical `hits` for every candidate. Equivalence is a precondition proved
before building, not a hoped-for outcome — and it is re-verified at runtime
(section 3). Also `k = (t*z) mod N` is never 0 for `1 <= t <= 1000 < N`, so
there is no `x = 0` edge case.

## 3 Equivalence verification

Nothing was timed until every gate below passed.

**Gate 1 — constants.** All three binaries' `--constants` output matches
`constants_expected.txt` on every key printed, with no missing keys.

**Gate 2 — self-verification against the exact integer reference.**
`reference.cpp` recomputes the search in pure integers (`k += z; if (k >= kN)
k -= kN;` and the window test `k*Q < P*N | k*Q >= (Q-P)*N`, max intermediate
2.0e8, far inside `uint64_t`). Checking both production implementations against
it is stronger than checking them against each other: it proves both correct
rather than merely mutually consistent.

```text
search_fp    --verify   candidates=100002/100002  hits_mismatches=0  MATCH
search_fp_b  --verify   candidates=100002/100002  hits_mismatches=0  MATCH
search_fx64  --verify   candidates=100002/100002  hits_mismatches=0  MATCH
```

**Gate 3 — cross-binary equivalence** (`equivalence.json`, `hits.csv`):

```text
FP-A  vs REF    compared=100002   mismatches=0
FP-B  vs REF    compared=100002   mismatches=0
FX64  vs REF    compared=100002   mismatches=0
FP-A  vs FX64   compared=100002   mismatches=0
FP-A  vs FP-B   compared=100002   mismatches=0
RESULT: PASS
```

Agreement on the derived answer as well as the per-candidate counts:

```text
              best_z   best_D bits           checksum   candidates
FP-A / FP-B     48     0x0000000000000000    2100000      100002
FX64            48     0x0000000000000000    2100000      100002
reference       48     0x0000000000000000    2100000      100002
```

The checksum has an independent closed form that confirms it. Summing `hits`
over all `z` and exchanging the order of summation: for each fixed `t`, the map
`z -> (t*z) mod N` is a bijection on `1..N-1`, so exactly the 2100 non-zero
in-window residues are counted once each. Over `T = 1000` steps that is
`1000 * 2100 = 2 100 000` — precisely the observed checksum, from all four
models.

`hits` ranges over `[10, 1000]` across candidates, so the search is genuinely
discriminating rather than degenerate, and 33 714 candidates attain the optimum
`hits = 21`. That is why the tie-break matters: the first-strict-improvement
rule is what makes `best_z = 48` deterministic and identical across
implementations, and `z = 48` is indeed the smallest such `z` (the closest any
`z < 48` gets is `|hits - 21| = 1`).

**Gate 4 — disassembly** (`asm_check.md`, `asm_*.txt`, `inner_*.txt`): FP's
wrap is branchless, FX64 has a single `add` update and no wrap instruction,
state is register-carried in both, no spills, no autovectorisation and no
closed-form substitution in either. Two fallbacks were required and are
documented there and in section 8.

**Gate 5 — FP-A / FP-B instruction equivalence:** MATCH instruction-for-
instruction, 13 vs 13 in the inner loop and 85 vs 85 across the whole timed
function, after normalising link-layout addresses. Independently confirmed by
`search_fp.cpp.o` being byte-identical (same MD5) in both targets. The FP-A/
FP-B pair is therefore a valid build-layout noise-floor reference.

**Every run agreed.** All 30 timed invocations reported the same `best_z`,
`best_D` bits, checksum and candidate count; `run_log.json` records zero
disagreements.

## 4 Measured times

30 invocations — 10 each of FP-A, FP-B and FX64 — interleaved in a fixed
recorded random order (seed 20260902, order in `run_order.txt`), every one
pinned with `taskset -c 6`. Longest contiguous same-variant streak: 3. Raw data
in `raw_times.csv`, one row per run.

```text
                n   median (ms)     min       max     sample stddev
FP-A           10     194.620     193.898   196.311      0.785
FP-B           10     194.904     193.837   201.955      2.476
FP pooled      20     194.620     193.837   201.955      1.849
FX64           10      25.841      24.919    27.442      0.886
```

Per inner iteration over 1.00002e8 iterations: FP 1.946 ns, FX64 0.258 ns.

FP-B's spread is dominated by a single 201.955 ms run; its median sits 0.15 %
from FP-A's. Medians are used throughout for exactly this reason, and the
outlier is retained rather than discarded — it inflates the pooled stddev and
therefore the threshold, which makes the verdict more conservative, not less.

## 5 Noise floor

```text
median(FP-A)      = 194.620 ms
median(FP-B)      = 194.904 ms
noise_floor_pct   = 100 * |194.620 - 194.904| / 194.620   =  0.1462 %
cv3_pct           = 3 * 1.849 / 194.620 * 100             =  2.8506 %
threshold         = max(0.1462, 2.8506)                   =  2.8506 %
```

FP-A and FP-B are the same `search_fp.cpp.o` behind a padding TU and a changed
link order, with instruction-identical hot loops. Their medians differ by
0.15 %, which bounds the contribution of build layout and code placement. The
threshold is set by run-to-run variability (3x the pooled coefficient of
variation), not by layout.

## 6 Decision

```text
FX64_speedup_pct = 100 * (194.620 - 25.841) / 194.620  = +86.7222 %
threshold        =                                        2.8506 %
FP / FX64 ratio  =                                        7.5314x
```

**86.72 % > 2.85 % -> margin present, in FX64's favour.** The rule is signed:
a negative speedup would mean FP is faster and would report "no margin". Here
the direction is unambiguous — FX64 is faster — and the margin exceeds the
threshold by a factor of 30. The separation is not marginal: FX64's slowest run
(27.442 ms) is more than seven times faster than FP's fastest (193.837 ms), so
the two distributions do not come close to overlapping and the verdict does not
depend on the choice of estimator.

## 7 Mechanism

The argument is from the measured *ratio* against the emitted dependency-chain
depth. No measurement is converted to cycles anywhere: the campaign records
wall-clock time only, and a ratio of two wall-clock medians taken on the same
pinned core minutes apart is clock-independent to first order.

**FP carries four operations on the recurrence.** The loop-carried chain on
`%xmm0` is

```text
vaddsd -> vcmpge_oqsd -> vandpd -> vsubsd
```

Each iteration cannot begin its add until the previous iteration's wrap has
resolved, because the wrap rewrites the state. The wrap is *explicit* — the
representation has no natural modulus at 1.0, so the reduction must be
programmed, and programming it branchlessly is what puts a compare, a mask and
a subtract on the critical path.

**FX64 carries one.** The chain is `add %rax,%rdx`, and nothing else. The
modular reduction is the integer add's own overflow at `2^64`; no instruction
is emitted for it at all. This is the whole mechanism: the wrap is implicit in
the representation, so it collapses out of the dependency chain rather than
extending it.

**Detection is off the critical path in both.** FP's two `vcomisd` reads and
FX64's `cmp`/`sbb` consume the post-update state but write only to `hits`,
which is not an input to the next state update. Neither implementation pays for
detection in chain depth; both pay only in issue slots.

**The measured ratio is consistent with that, and is a lower bound on the
inner-loop ratio.** 4-deep against 1-deep understates the gap, because chain
depth in *instructions* is not chain depth in *latency*: on this
microarchitecture the FP chain is two multi-cycle FP add/sub operations plus
two single-cycle ops, against a single single-cycle integer add. The measured
7.53x sits just below what that instruction mix implies, which is the expected
direction — both implementations also carry identical per-candidate work (the
`gcd` guard, the `alpha` computation, the metric evaluation and the
best-so-far update) that is on neither recurrence chain and dilutes any ratio
toward 1. Since that shared overhead is a *larger* fraction of FX64's much
smaller total, the 7.53x measured over the whole search is strictly less than
the ratio of the inner loops alone.

**The brief's stated expectation was not met, and in the informative
direction.** It anticipated roughly 3-4x, from FP at about 10-12 cycles per
step against FX64 at about 2-3. The observed 7.53x is roughly double that. The
FP side landed about where predicted; the discrepancy is on the FX64 side,
whose emitted loop is five instructions with a one-deep integer add chain and
no memory operand at all — materially cheaper per step than the 2-3 the brief
assumed. The direction agrees with the accumulator microbenchmark's 2.84x and
the magnitude exceeds it, which is notable given that this loop is scalar where
the microbenchmark's was 4-wide, and that this one additionally carries real
per-candidate setup the microbenchmark did not.

So the microbenchmark result does survive contact with a real workload. The
64.84 % tick reduction measured there under RDTSCP with no surrounding work
becomes an 86.72 % wall-clock reduction here, in a search where the recurrence
is the hot loop but is genuinely wrapped in per-candidate setup, metric
evaluation and bookkeeping.

## 8 Design choices and limits

**Why `T < N`.** Over a full period every candidate visits every residue
exactly once and `D` is constant, so no candidate could beat another. `T = 1000`
against `N = 100003` keeps each candidate on a `z`-dependent subset. Asserted
in `gen_constants.py`, and visibly true in the data: `hits` spans `[10, 1000]`.

**Why `eps*N` is non-integral.** It keeps every reachable point `k/N` off the
window edges — by 3.15e-07, six orders of magnitude beyond either
implementation's error bound. This is what makes bit-identical answers a
provable precondition rather than an empirical observation.

**The branchless FP wrap is the strongest fair baseline, so the result
understates FX64.** The wrap fires with probability about `alpha` and is
unpredictable for most `z`; a data-dependent branch would have loaded the
baseline with misprediction cost. GCC in fact emitted exactly that branch from
the natural source form, and gate 4 caught it; the fallback to scalar SSE
intrinsics restored the branchless form. Had it not been caught, the reported
speedup would have been larger and wrong.

**`alpha` and the `gcd` guard are inside the timed region** for both
implementations, because they are genuinely part of the search. Both cost the
same absolute time on both sides, and adding equal absolute time to both
numerator and denominator pulls a ratio toward 1 — so this choice makes the
reported speedup conservative. FX64 is charged more than FP here: its
`alpha_fixed` compiles to an out-of-line `__udivmodti4` call (one per
candidate, one per 1000 inner iterations), where FP's is a single `vdivsd`.

**`N` prime makes the coprimality filter trivially true.** `std::gcd(z, kN)` is
1 for every candidate, so the guard never rejects. It is retained for
faithfulness to the search definition as stated, and it compiles to a real
data-dependent binary-GCD loop in both binaries — identical absolute cost on
both sides, so again conservative.

**This measures a scalar search loop, not a vectorised one** — and that
understates the fixed-point representation's real advantage on this workload by
more than the framing suggests. Gate 4 found that GCC, left alone, recognises
`x += alpha` as an affine induction variable modulo `2^64`, substitutes the
closed form `x_t = t*alpha`, and vectorises FX64's inner loop **8 lanes wide**.
The FP loop cannot be transformed that way at any width: its conditional wrap
makes the recurrence non-affine, so there is no closed form to substitute. That
asymmetry is itself a consequence of the accumulator representation, and it is
a second, independent advantage stacked on top of the dependency-depth one
measured here. `#pragma GCC novector` was applied to *both* hot loops to hold
them to identical codegen constraints and keep the comparison on the question
the brief asks. **The autovectorised variant was not built or timed**, so no
number is claimed for it; the point is only that 7.53x is a floor, not a
ceiling, for what fixed point can do on this search.

**What this result does support.** On this machine, for this search, with these
flags: replacing a wrapped `double` accumulator with a 64-bit fixed-point
modular accumulator reduces end-to-end wall clock by 86.72 %, the answers are
bit-identical, and the cause is the collapse of the loop-carried dependency
chain from four operations to one.

**What it does not support.** It is one parameter set on one microarchitecture
under WSL2 with unobservable frequency governance. It does not establish a
speedup for vectorised implementations of either side, for other `(N, T, eps)`
where the per-candidate overhead is a different fraction of the total, for
window widths where the FP wrap becomes predictable, or for compilers other
than GCC 15.2 — the two codegen fallbacks needed here are direct evidence that
the emitted code, not the source, is what determines the result. It also says
nothing about accuracy: the parameter set was deliberately chosen so that
accuracy is *not* a discriminator, which is what makes the timing comparison
clean but also means no accuracy claim is being made.
