# summary.md — Wrapped FP vs Single-Lane 64-bit Fixed-Point Accumulator

**Decision:** `Decision FX64_margin_pct = 64.84` against
`Decision threshold = 6.40` — **margin present**, FX64 faster.

FX64 costs about 0.252–0.267 ticks per logical state against FP's 0.720–0.718, a
measured ratio of 2.84x.

### Timing mechanism

```asm
lfence
rdtscp
lfence

        timed workload

lfence
rdtscp
lfence
```

Implemented in `src/spike.hpp`:

```cpp
static inline uint64_t rdtscp_fenced(uint32_t* aux) {
    uint32_t lo, hi, a;
    __asm__ __volatile__(
        "lfence\n\t"
        "rdtscp\n\t"
        "lfence"
        : "=a"(lo), "=d"(hi), "=c"(a)
        :
        : "memory");
    *aux = a;
    return (static_cast<uint64_t>(hi) << 32) | lo;
}
```

* **CPU ordering** is explicit: both `LFENCE` instructions bracketing `RDTSCP`
  are emitted literally inside the asm template.
* **Compiler ordering** is explicit: `__asm__ __volatile__` with a `"memory"`
  clobber. `__volatile__` forbids deleting the statement or reordering it against
  other volatile/asm statements; `"memory"` forbids moving any memory access
  across it. The timed workload is a call to `run_loop`, declared
  `__attribute__((noinline, noclone))`, which reads and writes a `Ctx` object in
  memory — it is itself a memory access and cannot be hoisted above the opening
  barrier or sunk below the closing one.
* **Constraints**: `"=a"(lo)` and `"=d"(hi)` capture the 64-bit TSC value from
  EAX/EDX; `"=c"(a)` captures `TSC_AUX` from ECX.
* **Unit**: results are reported as `ticks`, the raw TSC delta. TSC ticks are not
  core cycles and no conversion to cycles is made anywhere in this report.

### TSC_AUX validation

Linux programs `IA32_TSC_AUX` as `(node << 12) | cpu`, and this is preserved
under the WSL2 hypervisor (verified independently: `taskset -c N` yields
`TSC_AUX == N` for N = 0, 3, 6, 11). The harness rejects a run unless both
`RDTSCP` reads return the same `TSC_AUX` **and** its low 12 bits equal
`sched_getcpu()`, which is the pinned logical CPU 6; it also re-reads
`sched_getcpu()` after the timed region and requires it unchanged. The driver
retries a rejected run up to 3 times and logs every rejection.

**All 180 runs passed on the first attempt: 0 rejections, 0 retries, 0 discarded
runs.** Every valid run is recorded in `raw.csv`.

## 3. Emitted Implementation

Full listings and the dependency argument are in `results/asm_check.md`; complete
`objdump -d -C` extracts are in `results/asm_fp_a.txt`, `results/asm_fp_b.txt`
and `results/asm_fx64.txt`.

Hot-loop shape, from `tools/loop_stats.py`:

```text
name    range         insns vector  stack  loads
FP-A    15c0-1673    39     36      0      0
FP-B    1600-16b3    39     36      0      0
FX64    15c0-161f    23     20      0      0
```

**Loop-carried dependency.** In both variants each of the four YMM state vectors
appears as both source and destination of its update, so the value produced at
iteration `t` is consumed at `t+1` (FX64: `%ymm8 %ymm7 %ymm6 %ymm5` through
`vpaddq %ymm4,%ymmN,%ymmN`; FP: `%ymm7 %ymm6 %ymm5 %ymm0` through `vaddpd` then
`vsubpd`). The four chains were not collapsed despite identical initial values,
because `init_ctx` passes every vector through an opaque
`asm volatile("" : "+x"(v))` barrier before storing it.

**No closed-form induction.** `%rax` is only incremented and compared against the
trip count `%rsi`; it never feeds any state. No `vmulpd` and no FMA against an
index appears in either body, despite `-mfma` being enabled, so nothing computes
`x0 + t*Delta`.

**No loop unrolling.** One copy of the four-state body per back-edge in both.

**FP wrap is branchless**, exactly as specified: `vcmpge_oqpd %ymm1,%ymmN,%ymm8`
/ `vandpd %ymm1,%ymm8,%ymm8` / `vsubpd %ymm8,%ymmN,%ymmN` per state vector. The
only transfer of control in the body is the loop back-edge. Detection reads the
post-wrap register.

**FX64 has no wrap instruction**; modulo-`2^64` is inherent in `vpaddq`.
Detection uses the folded bias: `vpaddq %ymm1,%ymmN,%ymm0` forms `state + Wb` and
`vpcmpgtq %ymm0,%ymm2,%ymm0` evaluates `Tb >s y`, which is
`(state + W_eps) <u 2*W_eps`. No `vpxor` appears in the loop because the bias
lives in the constants, computed outside the timed region.

**No state vector spills, either variant.** `stack` and `loads` are zero for all
three loops: no value at all is spilled or reloaded inside a hot loop. The only
memory references in either function are prologue loads and epilogue stores
against `Ctx`, outside the loop.

**Mask handling.** In both variants the mask is converted to a per-64-bit-lane
0/1 by `vpand` against a `_mm256_set1_epi64x(1)` broadcast and accumulated with
`vpaddq`, every iteration, for all 16 logical lanes. No `popcnt`, `vpmovmskb`,
`vextract*`, `vmovq` or `vpextrq` appears inside either timed region. All
detection operations are 64-bit-lane operations, so no 8-bit or 32-bit sublane
can contribute. Horizontal reduction to a scalar population count happens once,
in `reduce16`, after the closing timestamp and immediately before the `volatile`
sink.

**FP-A / FP-B instruction equivalence.** The hot loop moves from `0x15c0` to
`0x1600`, confirming link layout changed. Comparing the streams with
`tools/asm_norm.py`, which normalises away the absolute address column and
rewrites branch targets as relative offsets:

```text
instruction count: 60 vs 60
RESULT: MATCH instruction-for-instruction (mnemonics + operands; absolute
addresses and link-layout offsets normalised away)
```

**They match exactly.** No stop condition was triggered.

**Detection correctness.** Each binary was run with `--verify`, comparing its
vector detection total against an independent scalar model of one logical lane —
plain `double` arithmetic for FP, plain `uint64_t` arithmetic for FX64 — over the
same 1e7 iterations, multiplied by 16. All six implementation/eps combinations
returned `MATCH`.

```text

threshold(eps)       = max(noise_floor_pct(eps),
```

## 7. Boundary Divergences

Detection counts are not required to match. In this run **FP and FX64 did not
diverge at any eps**:

| eps | FP-A | FP-B | FX64 |
| --- | --- | --- | --- |
| 1e-6 | 288 | 288 | 288 |
| 1e-9 | 0 | 0 | 0 |
| 1e-12 | 0 | 0 | 0 |

Every one of the 180 invocations reported exactly the value shown; detection is
deterministic and reproduced identically across all runs of a given
implementation and eps. Totals are over all 16 logical states and all 1e7 timed
iterations. All 16 lanes carry the same trajectory (deviation 3), so 288 is
18 detections per lane x 16.

`tools/divergence_check.py` performs a stronger check than equality of totals: it
replays both scalar models for the full 1e7 iterations and compares the
**iteration indices** at which each detects.

```text
eps = 1e-6    FP 18 hits/lane, FX64 18 hits/lane, only-FP 0, only-FX64 0
eps = 1e-9    FP  0, FX64  0, only-FP 0, only-FX64 0
eps = 1e-12   FP  0, FX64  0, only-FP 0, only-FX64 0
```

There is no iteration at which one representation detects and the other does not.
Per-index detail is in `results/divergence.json`.

Where divergence would have appeared first: at `eps = 1e-6` the fixed-point
window half-width is `W_eps = 18446744073710` units of `2^-64`, while the
`double` grid spacing just below `1.0` is `2^-53`, i.e. 2048 such units — so the
two representations' window edges are far from coincident in absolute terms, and
agreement here means no trajectory point landed between them in 1e7 steps, not
that the boundaries coincide. At `eps = 1e-9` and `1e-12` neither representation
registered any detection, so agreement is trivially satisfied and carries no
information. The zero counts follow from the chosen `Delta` and iteration count;
they are not a defect and no algorithm was altered to change them.

## 8. Mechanism

**Primary: dependency-chain depth.**

The argument uses measured ratios and emitted operation counts only, so it does
not depend on absolute frequency or on the tick-to-cycle relationship. Per
iteration the two loops issue 36 (FP) and 20 (FX64) vector operations, and both
bodies are entirely register-resident, contend for the same Zen 3 vector pipes,
and touch no memory.

```text
predicted by vector op count   FP / FX64 = 36 / 20 = 1.80
measured (median over eps)     FP / FX64 = 2.84
excess over op-count prediction              +58%
```

If both loops were limited purely by how many vector operations they must issue,
the measured ratio would track 1.80. It does not: FP is 58% slower than its
operation count alone predicts, while FX64 has no comparable excess to hide. The
structural difference that accounts for it is visible in the disassembly. FP's
recurrence carries four dependent vector operations —
`vaddpd -> vcmpge_oqpd -> vandpd -> vsubpd` — whereas FX64's carries one,
`vpaddq`. In both variants detection and accumulation hang off the state as side
chains that never feed back into it, so they can overlap freely with the
recurrence.

That is the signature of **FP being dependency-chain-bound and FX64 being
throughput-bound**: FX64 is free to run at whatever rate its issue width allows,
because a 1-deep loop-carried chain imposes essentially no serialisation across
its four independent state vectors; FP is held back by the serialised update its
explicit wrap creates, so its extra work does not simply add to a throughput
total, it sits on the critical path.

**Secondary contribution: implicit modulo-`2^64` wrap.** This is the *cause* of
the asymmetry rather than a separate mechanism — FX64's wrap is free because it
is inherent in `vpaddq`, which is exactly why its recurrence is one operation
deep, and it also accounts for 12 of FP's 36 vector operations (the compare, and
and subtract, times four state vectors).

Stated limitation: the methodology forbids update-only and detect-only runs, so
this attribution rests on the measured ratios plus the emitted dependency
structure rather than on a direct decomposition, and hardware performance
counters were not used.

## 9. Verdict

```text
margin present
```

`Decision FX64_margin_pct = 64.84 > Decision threshold = 6.40`, so a margin is

logical state than the wrapped AVX2 `double` baseline, with detection inside the
timed region in both cases.

## 10. Deviations

1. **FX64 detection comparison orientation corrected.** The task specification
   gave the detection step as
   `__m256i cmp = _mm256_cmpgt_epi64(y, Tb);` with `y = state + Wb`,
   `Wb = W_eps + 2^63`, `Tb = 2*W_eps + 2^63`. That is the complement of the
   intended predicate: `y` is the sign-biased form of `state + W_eps`, and the
   window test is `(state + W_eps) <u 2*W_eps`, which under sign-bit biasing is
   `Tb >s y`, i.e. `_mm256_cmpgt_epi64(Tb, y)`. As written it would have counted
   roughly 1.6e8 detections instead of 288 and would have failed the independent
   scalar cross-check. The implementation uses the correct orientation; the
   biased constants `Wb` and `Tb` are exactly as specified, and the emitted
   instruction is still a single `vpcmpgtq`, so the operation count and the
   comparison are unaffected.
2. **`-std=c++20` is carried in `CMAKE_CXX_FLAGS`** via `CMAKE_CXX_STANDARD`, as
   the task requires C++20. It is not an optimisation-changing flag and is
   byte-identical across all three binaries. `CMAKE_BUILD_TYPE` is forced empty
   so no `-O`/`-DNDEBUG` is added behind it, and IPO/LTO is disabled.
3. **All 16 lanes carry the same trajectory.** Both implementations are
   initialised from the same mathematical `x0` and `Delta` with no separately
   chosen per-lane constants, so every lane follows one trajectory. The 16 states
   are independent as *dependency chains* — four separate YMM registers each
   loop-carried, never collapsed, guaranteed by the opaque init barriers — but
   not as distinct trajectories. This is why detection counts are exact multiples
   of 16.
4. **`fp_b` uses both permitted noise-floor mechanisms.** The specification calls
   for "changed link order + padding TU"; `fp_b` applies both, linking
   `padding.o` first and moving `harness.o` after `fp_double.o`. The
   instruction-equivalence precondition was still satisfied exactly.
5. **Sign-bit bias folded into the constants.** Because `x + 2^63 == x ^ 2^63`
   modulo `2^64`, the bias is applied to `W_eps` and `2*W_eps` once, outside the
   timed region, exactly as the specification's `Wb`/`Tb` precomputation intends.
   The loop therefore emits `vpaddq`/`vpcmpgtq` with no `vpxor`.
6. **Warm-up state is reset after warm-up, outside timing**, so the reported
   `detections` covers exactly the 1e7 timed iterations rather than 1.05e7.
   Warm-up and the timed run share the one `noinline, noclone` `run_loop`, so
   they exercise the same instructions.
7. **An `--constants` and a `--verify` mode were added to the harness.** Both run
   entirely outside any timed region and neither affects the measured code path;
   they implement validation requirements 3 and 4.
8. **Turbo could not be disabled from inside the guest.** WSL2 exposes no cpufreq
   or governor interface; boost is host-controlled and was left enabled. Recorded
   as an environment observation rather than corrected for.
9. **Sibling occupancy is reported at jiffy resolution**, which is coarse relative
   to the ~15 ms invocation. Stated as a bound on what the observation supports
   rather than as a claim of quiescence. No run was discarded for sibling
   activity.
10. **Shared provenance.** `src/spike.hpp`, `src/harness.cpp`, `src/fp_double.cpp`,
    `src/fixed_u64.cpp`, `src/padding.cpp` and `tools/asm_norm.py` /
    `tools/loop_stats.py` are shared with the earlier spike in the parent
    directory, adapted for this two-variant tree (FX128 support removed, binaries
    renamed `fp_a`/`fp_b`/`fx64`). This tree is self-contained: it builds, runs
    and analyses without reference to the parent directory.
